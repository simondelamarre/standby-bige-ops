# standby-bige-ops

Put a cloud stack to sleep when nobody uses it, and wake it up cleanly on the
next visit.

A tiny guardian VM sits next to the stack, behind the same load balancer. While
the app is up, the load balancer sends every request straight to the app and the
guardian stays out of the way. When the stack sleeps, the guardian becomes the
only healthy backend: the first visit starts the stack again, in the right
order, and every visitor sees a waiting page with the progress of the restart.

```
browser ──► load balancer ──► app VM ──► data VMs        (stack awake)
                         └──► guardian VM ──► cloud API  (stack asleep)
```

- **Out of the request path.** The guardian never proxies live traffic. It
  switches through the load balancer health check: it reports healthy only while
  the app sleeps.
- **Sleeps after real idleness.** The stack goes to sleep only after
  `idle_after` (60 min by default) without any incoming traffic, measured by a
  tiny probe on the app VM. An optional schedule keeps it awake during office
  hours.
- **Wakes on the first visit.** No click needed; later visits show the progress
  instead of starting it again. A start button is available as an option.
- **Ordered.** Machines start in waves (databases first, then the app), each
  wave checked by real probes before the next one.
- **Bounded.** Caps on wake-ups per day and awake hours per month limit what
  robots can cost you.
- **Small and auditable.** One static Go binary, standard library only, no
  telemetry. Its only outbound calls go to the cloud API and the stack's own
  machines.

It is built for [bige-ops](https://bige.dev), which generates the manifest and
the configuration from a simulation, but nothing here depends on bige-ops: a
fork only needs a manifest and a configuration file.

## Try it locally

You need Docker. Nothing else is installed on your machine: builds and tests run
in the official Go image.

```bash
make test
make local-up
open http://localhost:8088
```

The demo runs a load balancer (Caddy, standing in for the cloud load balancer),
a sample app with its activity probe, a Redis "database" and the guardian.
`idle_after` is 1 minute in the demo, so the stack falls asleep quickly:

```bash
make local-logs      # watch the guardian decide
make local-down
```

## Awake hours

One simple rule: inside the awake ranges the stack stays up, even without
traffic. Outside them it sleeps after `idle_after` without traffic, and wakes on
the next visit (or on a click, if you prefer the button).

```json
{
  "schedule": {
    "timezone": "Europe/Paris",
    "days": ["mon", "tue", "wed", "thu", "fri"],
    "awake": ["08:00-12:00", "14:00-18:00"]
  },
  "idle_after": "60m",
  "wake": { "on_visit": true, "button": false, "schedule": true }
}
```

- `wake.on_visit: true` — a visit wakes the stack automatically.
- `wake.on_visit: false, wake.button: true` — visitors click "Start".
- `wake.schedule: true` — the stack wakes when a range opens (8:00, 14:00).
- No `schedule` at all — on demand only, for a staging for instance.

The idle clock starts once the last connection to the app closes. Load
balancers keep their backend connections open for a while after the last
request (about 60 s on an Outscale LBU, 2 min with the Caddy of the local demo),
so the stack falls asleep `idle_after` plus that delay after the last request.

## Why

- **Money.** A sleeping machine no longer bills compute. Disks, public IPs and
  the load balancer still do, and bige-ops shows them before you enable
  standby. Reserved machines are paid whatever happens: standby only helps on
  demand.
- **Resources.** A machine that sleeps leaves the processor and memory of its
  host free. Less work means less electricity, less heat, so less energy and
  water spent on cooling. We do not publish a figure per machine: it depends on
  the data centre. We measure what can be measured: the hours your stack sleeps.

GitHub Pages.

## How it works

| Piece | Where it runs | Role |
|---|---|---|
| `standby run` | guardian VM | Reads the state from the cloud API, applies the schedule and the idle rule, starts and stops machines, serves the waiting page and its health endpoint |
| `standby tap` | app VM | Counts incoming connections on the app port and answers the load balancer health check on a separate port, so health checks never count as traffic |

The guardian reads two files:

- **`manifest.json`**, generated by bige-ops: the machines it may drive, in wake
  order, with their probes. Any machine outside the manifest is refused.
  Schema: [`schemas/manifest.schema.json`](schemas/manifest.schema.json).
- **`config.json`**: schedule, idle delay, caps, waiting page.
  Schema: [`schemas/config.schema.json`](schemas/config.schema.json).

The waiting page answers `503` with `Retry-After`, polls
`/_standby/status` (schema: [`schemas/status.schema.json`](schemas/status.schema.json))
every 3 seconds and reloads once the app is ready. Without JavaScript it
reloads every 60 seconds. `/robots.txt`, `/favicon.ico` and `/.well-known/*`
never wake the stack.
